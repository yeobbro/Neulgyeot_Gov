# 웨어러블(스마트링·스마트워치) 연동 기획서

> 늘곁 지자체용 고도화 · 기획 v0.1 · 작성일 2026-11-25
> 범위: **지자체용(재가 돌봄) 우선**, 병원용·직원 착용은 확장 단계로 정의
> 상태: Phase 0(계약·수신 API·신호 규칙·담당자 화면) 구현 — **합성 데이터·mock 게이트웨이만**, 실제 기기·제조사 클라우드 연결 없음

---

## 1. 왜 하는가

통합돌봄 대상자 중 독거·고령 대상자는 정기 모니터링(기본 30일 주기) 사이의 변화를 담당자가 알기 어렵습니다. 지금 늘곁은 **방문·전화로 확인한 결과만** 기록합니다.

스마트링·워치는 착용 여부, 활동량, 수면, 안정 시 심박 같은 **생활 리듬 정보**를 매일 남깁니다. 이 정보를 담당자 업무 흐름에 연결하면:

| 지금 | 연동 후 |
|---|---|
| 30일마다 일괄 전화·방문 | 평소와 다른 대상자를 먼저 확인 (우선순위 기반 모니터링) |
| 이상 징후는 대상자·가족이 먼저 연락해야 알 수 있음 | "3일째 활동량 평소의 40%" 같은 **설명 가능한 신호**가 업무로 생성 |
| 서비스 효과를 만족도 설문으로만 판단 | 서비스 시작 전후 활동·수면 변화를 참고 지표로 확인 |

**하지 않는 것** — 이 기능은 의료기기·응급 관제가 아닙니다.

- 진단, 질병 예측, 응급 여부 판정을 하지 않습니다. 모든 신호는 "확인 필요"이며, 판단은 담당자가 합니다.
- **낙상·SOS의 실시간 응급 대응 경로가 아닙니다.** 늘곁은 하루 단위 요약을 받으므로 늦게 도착합니다. 실시간 대응은 기기 사업자의 관제·보호자 알림, 응급안전안심서비스, 119 등 기존 체계가 담당해야 하며, 늘곁은 사후 확인·기록 업무만 만듭니다. (화면·계약 문서에 모두 명시)
- 원시 생체 스트림(초 단위 심박, PPG, 위치)을 받지 않습니다.

## 2. 대상 시나리오

| 구분 | 착용자 | 기기 | 늘곁에서 쓰는 곳 | 단계 |
|---|---|---|---|---|
| **A. 재가 안부·생활리듬** | 통합돌봄 대상자(독거 우선) | 스마트링(수면·심박·착용), 스마트워치(+걸음·낙상감지·SOS) | 사례 상세 `웨어러블` 탭, 확인 업무, 업무 타임라인 | **Phase 0~1** |
| B. 방문 서비스 체크인 | 서비스 제공기관 직원 | 스마트워치 | 방문 시작·종료 확인 → 서비스 제공 결과(`service_delivery_events`) | Phase 3 |
| C. 병원→지자체 연속 착용 | 퇴원 환자 | 병원에서 쓰던 링·워치 | 퇴원 연계 시 기기 이관 동의, 지자체 수신 계속 | Phase 4 |

시나리오 B·C는 병원용 저장소의 `lib/care/wearables.ts`(직원 워치·링 태깅 어댑터, NFC 미지원 기기는 QR fallback) 설계를 그대로 따릅니다 — 모든 기기가 NFC·앱 연동을 지원한다고 가정하지 않고, 어댑터가 기능(capabilities)을 선언합니다.

## 3. 연동 구조

```
[스마트링/워치] ─BLE→ [제조사 앱 · Health Connect · HealthKit]
                               │  (기기 사업자/수집 게이트웨이 — 늘곁 외부, 협약 대상)
                               ▼
        POST /api/integrations/wearables/daily-summaries   (일 단위 요약만, Bearer + scope)
                               │
             ┌─────────────────┼────────────────────────┐
             ▼                 ▼                        ▼
   동의 범위 검사        wearable_daily_summaries   신호 규칙(개인 기준선 비교)
   (범위 밖 → 422)        (기기·날짜별 upsert)              │
                                                         ▼
                                     wearable_signals ─→ action_tasks(wearable_check) ─→ 담당자 알림
                                                         │
                                     담당자 확인/해당 없음 처리 → 필요 시 모니터링 기록·계획 변경
```

**설계 결정**

1. **늘곁은 제조사 SDK를 직접 붙이지 않습니다.** 기기마다 데이터 접근 방식이 다르고(Health Connect·HealthKit은 기기 내 API, 링 제조사는 자체 클라우드), 계약·보안 심사도 제각각입니다. 늘곁은 **제조사 중립 계약(DEMO v0.1)** 을 정의하고, 협약한 게이트웨이(기기 보급 사업자 또는 늘곁 동반 앱)가 이를 구현합니다.
2. **하루 요약만 받습니다.** 개인정보 최소 수집 원칙, 그리고 실시간 관제로 오해받지 않기 위해서입니다.
3. **기존 병원 연계와 같은 인증 체계**를 씁니다 — `integration_clients`, 해시 저장 API 키, scope(`wearables:write`). 운영 시 OAuth 2.0 client credentials·mTLS로 교체(병원 연계와 동일한 로드맵).
4. **(기기, 날짜) 기준 upsert라 재전송에 안전**합니다. 같은 날 요약을 다시 보내면 최신 값으로 갱신되고, 같은 신호는 중복 생성되지 않습니다.

## 4. 수신 계약 (DEMO v0.1)

`POST /api/integrations/wearables/daily-summaries`
Headers: `Authorization: Bearer <client key>` (scope `wearables:write`), `X-Trace-Id`(선택)

```json
{
  "schemaVersion": "0.1",
  "deviceRef": "SYN-RING-0003",
  "summaries": [
    {
      "date": "2026-11-24",
      "wearMinutes": 1310,
      "steps": 2140,
      "activeMinutes": 35,
      "sleepMinutes": 410,
      "restingHeartRate": 66,
      "heartRateMin": 54,
      "heartRateMax": 118,
      "spo2Min": 93,
      "fallEvents": 0,
      "sosEvents": 0
    }
  ]
}
```

| 규칙 | 응답 |
|---|---|
| 등록되지 않았거나 다른 게이트웨이의 `deviceRef` | 404 `DEVICE_NOT_REGISTERED` |
| 동의 철회·일시중지 기기 | 422 `CONSENT_NOT_ACTIVE` (저장 안 함) |
| 동의하지 않은 항목이 들어 있음 (예: 수면만 동의했는데 심박 전송) | 422 `CONSENT_SCOPE_VIOLATION` (전체 거부, 저장 안 함) |
| 미래 날짜, 31일 초과 묶음, 범위 밖 수치 | 400 `VALIDATION_FAILED` |
| 정상 | 200 `{ accepted, signalsCreated, traceId }` — 대상자 정보·신호 내용은 돌려주지 않음 |

항목 ↔ 동의 범위 매핑: `wear`(wearMinutes, 필수) · `activity`(steps, activeMinutes) · `sleep` · `heart_rate`(restingHeartRate, heartRateMin/Max) · `spo2` · `fall` · `sos`.

## 5. 신호 규칙 (설명 가능, 개인 기준선 비교)

기준선 = 해당 날짜 **이전 14일 중 충분히 착용한 날(≥ 10시간)의 중앙값**. 유효한 날이 5일 미만이면 비교형 신호를 만들지 않고 "기준선 부족"으로 표시합니다 (무응답 ≠ 정상 원칙과 같은 맥락: 데이터 부족을 "이상 없음"으로 보지 않음).

| 신호 | 조건 | 표시 문구(예) | 업무 기한 |
|---|---|---|---|
| `fall_reported` 낙상 감지 기록 | fallEvents ≥ 1 | 기기가 낙상 감지를 1회 기록했습니다. 실제 낙상 여부는 확인되지 않았습니다. | 당일 |
| `sos_reported` SOS 기록 | sosEvents ≥ 1 | 기기에 SOS 버튼 기록이 있습니다. 실시간 대응 여부를 기기 사업자에 확인하세요. | 당일 |
| `no_data` 수신 없음 | 마지막 요약이 48시간 이상 전 | 48시간 이상 요약이 수신되지 않았습니다. (미착용·충전·통신 확인) | +1일 |
| `low_wear` 착용 부족 | wearMinutes < 240 | 착용 시간 3시간 10분 — 미착용 또는 충전 상태 확인 | +1일 |
| `activity_drop` 활동량 감소 | steps < 기준선의 50% (기준선 ≥ 500보) | 걸음 수 820보, 평소(중앙값 2,600보)의 32% | +1일 |
| `sleep_change` 수면 변화 | \|수면 − 기준선\| ≥ 120분 | 수면 9시간 50분, 평소 7시간 10분 대비 +160분 | +1일 |
| `resting_hr_change` 안정 시 심박 변화 | \|안정 시 심박 − 기준선\| ≥ 15bpm | 안정 시 심박 84bpm, 평소 66bpm 대비 +18 | +1일 |
| `spo2_low_reported` 낮은 산소포화도 기록 | spo2Min < 90 | 기기 측정 최저 산소포화도 88% 기록 — 측정 오류 가능, 확인 필요 | 당일 |

- 임계값은 `lib/domain/wearable.ts`의 `SIGNAL_RULES` 한 곳에 있습니다. 파일럿 후 지자체 설정값으로 분리합니다.
- 신호마다 근거(값·기준선·임계값·기준선 일수)를 저장하고 화면에 그대로 보여 줍니다.
- 한 사례에 열린 `wearable_check` 업무가 있으면 새 업무를 만들지 않고 신호만 묶습니다 (업무 폭주 방지). 신호를 모두 처리하면 업무가 자동 완료됩니다.

## 6. 개인정보·권한

| 항목 | 설계 |
|---|---|
| 법적 근거 | 건강 관련 정보 → 개인정보 보호법 제23조 민감정보. **항목별 별도 동의** 기록(`wearable_consents.metrics`, 근거, 동의 일시, 보유기간). 동의 없는 항목은 수신 단계에서 거부 |
| 철회 | 담당자가 철회 처리 → 기기 일시중지, 이후 수신 거부(422). 기존 요약의 파기 시점은 보유기간 정책에 따름 |
| 최소 수집 | 하루 요약만, 위치·원시 파형 없음. 기기 식별자는 게이트웨이 발급 참조값(`deviceRef`)만 |
| 열람 | 사례 열람 권한자(관리자·권역 내 사례관리 담당자)만. **서비스 제공기관·감사 담당자 화면에는 노출하지 않음** |
| 수정 | 기기 등록·동의 철회·신호 처리는 배정 담당자 또는 관리자 |
| 감사 | `wearable.register`, `wearable.consent_withdraw`, `wearable.intake`, `wearable.signal_review`, `wearable.view` — 메타데이터만(수치·메모 미기록) |
| 격리 | 신규 4개 테이블 모두 RLS 테넌트 격리 |
| 남은 검토 | 게이트웨이 사업자 위탁계약, 국외 클라우드 경유 여부, 보유기간(기본 90일 제안), 영향평가 범위 — `PRIVACY_AND_LEGAL_REVIEW.md`에 추가 |

## 7. 화면

- **사례 상세 → `웨어러블` 탭** (신규)
  - 동의·기기 패널: 동의 항목, 근거, 보유기간, 기기 종류·참조값, 마지막 수신 시각, 철회 버튼
  - 확인 필요 신호: 문구 + 근거, `확인 완료`/`해당 없음` 처리(메모)
  - 최근 14일 요약표: 착용·걸음·수면·안정 시 심박·최저 SpO₂·낙상/SOS. 동의하지 않은 항목은 `미동의`, 값 없음은 `—`
  - 상단 고정 안내: "응급 대응 경로가 아닙니다"
- **업무 목록**: 새 업무 유형 `웨어러블 확인 필요`
- **업무 타임라인**: 신호 생성·처리 이력 포함

## 9. 성과 지표 (파일럿)

- 착용률: 대상자별 하루 10시간 이상 착용한 날 비율 (목표 70%↑)
- 신호→확인 소요시간 중앙값 (목표 1영업일 이내)
- 신호 정밀도: `확인 완료` / (`확인 완료` + `해당 없음`) — 낮으면 임계값 조정
- 정기 모니터링 외 추가 확인 건수, 그중 계획 변경으로 이어진 비율
- 담당자 1인당 주간 확인 업무량 (과부하 여부)

## 10. 위험과 대응

| 위험 | 대응 |
|---|---|
| 응급 관제로 오인 | 화면·계약·교육자료에 명시, 낙상/SOS는 "사후 확인" 업무로만 생성, 실시간 경로는 기기 사업자 책임으로 협약 |
| 오탐으로 업무 폭주 | 사례당 열린 업무 1건으로 묶기, 정밀도 지표로 임계값 조정 |
| 미착용을 "이상 없음"으로 오해 | `no_data`·`low_wear` 신호, 기준선 부족 표시 |
| 고령자 기기 사용 어려움(충전·착용) | 링 우선 권장(충전 주기 김), 제공기관 방문 시 착용 확인 항목 추가 |
| 제조사별 데이터 정의 차이 | 계약에 항목 정의·단위 고정, 게이트웨이에서 변환 책임 |
